# 【要点まとめ】Next.js認証で「ログイン者のみGemini会話」

> 詳細版は [njsnindyou.md](njsnindyou.md)。これはチーム共有・発表用の1枚まとめ。

---

## 結論（3行）

1. **技術的には実装できる。** Auth.js v5（旧NextAuth）+ Googleログインで実現可能。**今回は Auth.js v5 で進める**（下記の通りbetaでも実用上OK）。
2. でも本アプリは **DV相談アプリ**。「そもそもログイン必須にしてよいか」の判断のほうが重い。
3. 進め方：**目的とDV安全性をチームで合意 → BFF方式でPoC**。いきなり全体実装しない。

### 使うライブラリ：Auth.js v5（`next-auth@beta`）— betaでも進めてよい理由

- **セキュリティ修正は継続すると公式が明言**：「we'll keep addressing security patches and urgent issues」— [Better Auth公式ブログ](https://better-auth.com/blog/authjs-joins-better-auth) / [GitHub Discussion #9511](https://github.com/nextauthjs/next-auth/discussions/9511)
- **2023年から多数の本番アプリで使われてきた実績**（beta表記は「API調整中」の意味）— [LogRocket 2026](https://blog.logrocket.com/best-auth-library-nextjs-2026/)
- ⚠️ ただし：**公式が「production-ready」と明言した出典は無い**／新機能は増えない（メンテナンスモード）。将来要件が増えたら **Better Auth** への移行を検討する前提で採用。

## なぜ「フロントにログイン」だけではダメか

```
ブラウザ → Next.js(フロント) → FastAPI(:8000) → Gemini
             鍵をかけても…      ここが無防備なら素通り
```

- Geminiを呼ぶのは**別プロセスのFastAPI**。フロントに鍵をかけても、`curl` で直接APIを叩けば**誰でもGeminiを使えてしまう**。
- → **バックエンドの守り方**まで設計して初めて「ログイン者のみ」が成立する。

---

## 実装方式：**方式A（BFF）を推奨**

| | 方式A（BFF）★推奨 | 方式B（JWT検証） |
|---|---|---|
| やり方 | Next.js経由でGeminiを呼ぶ。途中で未ログインを弾く | FastAPIが自分でトークン検証 |
| トークン | ブラウザに出さない（安全） | ブラウザに出す（穴があると盗まれうる） |
| 改修量 | 小さい（`api.ts`の向き先を変えるだけ） | 多い |
| 向き | **1チーム/1リポジトリの今回向き** | 外部公開・別クライアント向き |

> ※Bが危険なのではない。**Aはリスク経路を1つ減らせて得**、という判断。

## ⚠️ 最大の論点：DVアプリとしての安全性

このアプリの根幹は「**加害者に見られない・痕跡を残さない・すぐ消せる**」。ログインはこれと衝突しうる。

- **Googleログイン＝足がつく**：Googleアカウントに利用記録が残る。加害者が監視していると致命的（アプリ側では消せない）。
- **「すぐ閉じる」と相性が悪い**：画面を消してもログインCookieが残り、再訪でバレうる。
- **会話履歴の扱い**：ユーザーに永続保存すると、すぐ閉じても消えず再ログインで復活してしまう。

### チームで先に決めること
1. **なぜログインが必要？**（履歴保存／不正利用対策／有料化…）→ 目的次第で「Google必須」以外の解もある
2. **必須か任意か**（匿名利用を残すか）
3. **痕跡が残る件をどう受容/緩和するか**
